# API Client & Types

## `apiClient<T>()` Abstraction

All API calls from Zustand stores and context providers go through a single fetch wrapper in `lib/api-client.ts`:

```typescript
async function apiClient<T>(endpoint: string, options?: RequestInit): Promise<T> {
  // Prepend /api if not already present
  const url = endpoint.startsWith('/api') ? endpoint : `/api${endpoint}`

  const response = await fetch(url, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...getAuthHeaders(),      // { Authorization: 'Bearer <token>' } | {}
      ...options?.headers,
    },
  })

  if (response.status === 204) return undefined as T  // No Content

  const data = await response.json()

  if (!response.ok) {
    throw new Error(data.message ?? 'Request failed')
  }

  return data as T
}
```

**Responsibilities**:
- URL normalization (always absolute `/api/*`)
- Auth header injection from `localStorage` token
- 204 handling (DELETE endpoints)
- Error normalization (throws `Error` with `data.message`)

**Limitations**: No retry logic, no request deduplication, no caching. Each store manages its own `isLoading` flags. Caching is handled by Zustand's persisted state.

## Next.js API Proxy

`next.config.ts` rewrites `/api/*` requests to the Rust backend. All client-side API calls use relative URLs (`/api/...`) — no direct references to the backend host. This means:

1. CORS is never an issue in production (same-origin from the browser's perspective)
2. The backend URL is a server-side secret (not exposed to the browser)
3. Next.js can add request headers or transform responses at the proxy layer

## Zod Schema Validation

`lib/api-types.ts` defines Zod schemas for every API response type. Stores validate API responses before writing to state:

```typescript
// In admin-store.ts:
const parsed = AdminStatsSchema.safeParse(data)
if (!parsed.success) {
  set({ error: 'Invalid response from server', isLoading: false })
  return
}
set({ stats: parsed.data })
```

## Health Response

```typescript
interface HealthResponse {
  status: string     // "healthy"
  version: string    // semver
  uptime_seconds: number
}
```

The client calls `GET /api/health/api` and `GET /api/health/intelligence` to display system status in the admin dashboard.
